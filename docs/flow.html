Pre-Exercise Tutorial

How The GenAI Challenge/Lab Actually Works

The workshop is intentionally split across two applications. The Java app is the fixed lab environment and data service. The Python MCP app is the GenAI layer participants inspect and improve. If participants understand that split first, the exercise flow makes much more sense.

What participants change The Python MCP app. This is where routing, tool use, prompts, overlays, and answer shaping live.
What participants do not change The Java app. Treat it as the fixed command centre and banking data service for the lab.
Why the split exists It separates product logic from source data. The agent must ask for evidence instead of reading everything directly.

The Two Apps

This repo is only half of the system. Participants are working on the Python side, but the experience depends on both applications running together.

Java App

Immutable lab backend

The Java application serves two purposes during the workshop.

  • It is the command centre for the hackathon or lab flow.
  • It exposes REST endpoints with dummy customer data, alerts, transactions, and related evidence.
  • Participants should treat it as fixed infrastructure.
  • The agent does not access the database directly. It can only see what the Java API returns.
  • This constraint is deliberate. It forces evidence retrieval to happen through explicit tools.
Python MCP App

Mutable GenAI layer

The Python application is where the agent behavior lives.

  • It provides the Streamlit UI participants interact with.
  • It decides which tool to call for a user request.
  • It calls the Java REST API through Python tool wrappers.
  • It formats the answer deterministically or asks a live LLM to write the final response.
  • This is the side participants inspect, reason about, and improve.
  • Most workshop lessons are about making this layer retrieve the right evidence and respect the right boundaries.

What A Tool Means In This Workshop

A tool is not magic. In this project, a tool is a controlled Python function that calls a specific Java endpoint and returns structured evidence. Tools are the bridge between the LLM-facing app and the fixed banking data service.

Narrow tools

Single-purpose evidence fetches such as customer profile, alerts, transactions, or spending summary.

get_customer_profile, get_alerts, get_transactions

Composite tools

Multi-call evidence packages built by the Python layer when one endpoint is not enough for the task.

get_customer_profile_and_alerts, get_full_picture

Why tools matter

Most failures in the exercises come from choosing the wrong tool, using incomplete evidence, or interpreting a tool result badly.

Block Diagram

This is the simplest end-to-end sequence to keep in mind. Every exercise is changing some part of this path.

1. User Request

A participant asks a banking question in the chat UI.

2. Streamlit UI

The Python app sends the prompt into the agent flow.

3. Agent Graph

run_agent(...) coordinates decision, execution, and response steps.

4. Tool Selection

The Python side chooses the evidence path using deterministic logic or an LLM router.

5. Python Tools

Tool wrappers translate that choice into one or more API calls.

6. Java REST API

The immutable Java app returns dummy customer evidence as JSON.

7. Answer Layer

The Python app formats the evidence directly or sends it to the LLM for grounded answer generation.

8. Final Response

The participant sees the answer plus any trace or tool details exposed by the UI.

Request Lifecycle

This is the main end-to-end flow participants should remember. One user prompt can involve two different LLM moments: first for tool selection, then later for answer generation.

Step-by-step path

1
User asks a question in the Python UI.

The Streamlit app sends the prompt into run_agent(...) in app/agent/graph.py.

2
The Python app decides what evidence is needed.

Routing happens in app/agent/nodes/tool_decision.py. Depending on configuration, this may be deterministic keyword logic or a live LLM tool-choice call.

3
The chosen tool maps to one or more Java API calls.

Execution happens in app/agent/nodes/tool_execution.py. Python calls the Java REST endpoints through wrappers under app/tools/.

4
The Java app returns structured dummy banking data.

The Python side receives JSON for customer records, alerts, transactions, or spending summaries.

5
The Python app decides how the final response should be produced.

Formatting happens in app/agent/nodes/response_formatter.py. Some cases use deterministic formatting. Other cases send the retrieved tool result to a live LLM to write the answer.

6
If live LLM mode is on, the LLM is called again.

The second LLM call is not for tool choice. It is for grounded answer generation using the selected tool result plus the active prompt and format contract.

7
The answer and trace return to the UI.

Participants see the visible answer, and the workshop can also expose details about selected tool, raw payload, and routing trace.

Architecture Layout

A simple way to think about the system is: interface, decision, retrieval, then response.

Interface

app/ui.py runs the Streamlit chat experience participants use.

The user prompt starts on the Python side, not in Java.

Decision

app/agent/nodes/tool_decision.py decides which tool should be used.

This is where many exercises focus: wrong route, incomplete route, over-broad route, or boundary failure.

Retrieval

app/tools/*.py wraps the Java REST API.

The Java app exposes the evidence. The Python app collects it into usable packages.

Response

app/agent/nodes/response_formatter.py turns retrieved evidence into the answer the participant sees.

That answer may be deterministic, LLM-generated, or constrained by explicit response policy.

Important mental model The LLM is not the data source. The Java app is the data source. The Python agent must first retrieve evidence through tools, then answer from that evidence.

Java REST Surface The Python Tools Use

Participants do not need to memorize every endpoint, but they should understand that the Python tools are thin wrappers around a small banking API surface.

Customer profile

GET /api/banking/customers/{customerId}

Used when the request is really about who the customer is, their status, and their risk profile.

Alerts

GET /api/banking/alerts?customerId=...&severity=...

Used for alert evidence such as investigations, review notices, and operational warnings.

Transactions

GET /api/banking/transactions?customerId=...&fraudOnly=...

Used when recent activity or fraud signals matter more than the static profile alone.

Spending summary

GET /api/banking/spending-summary?customerId=...&groupBy=category

Used for compressed activity summaries instead of raw transaction-by-transaction inspection.

Where The LLM Appears

Participants often assume there is one single LLM call. In practice there can be two separate LLM jobs.

LLM call 1: tool selection

In semantic-router mode, the LLM receives the user prompt, the allowed tool set, tool descriptions, and the system prompt. Its job is to return a structured tool choice.

  • Question: what evidence should we fetch?
  • Output: tool name plus structured tool input.
  • Code path: choose_tool(...) in app/llm/factory.py.

LLM call 2: answer generation

After the tool result comes back, the LLM may be asked to write the user-facing answer. This second call should stay grounded in the retrieved evidence.

  • Question: how do we explain the evidence clearly?
  • Input: selected tool plus tool result plus answer-format contract.
  • Code path: generate_answer(...) in app/llm/factory.py.

Where To Look In The Code

These are the files most worth showing participants when you want them to understand the system quickly.

Entry point

app/ui.py and app/agent/graph.py

This shows where a user prompt enters the agent flow.

Routing

app/agent/nodes/tool_decision.py

This is the main workshop learning surface for choosing the right evidence path.

Tool wrappers

app/tools/customer.py, alerts.py, transactions.py, spending_summary.py

These show the bridge from Python into the Java REST API.

Answer generation

app/agent/nodes/response_formatter.py and app/llm/factory.py

This is where evidence becomes the final visible answer.

Short version for participants: Java holds the lab and the data. Python holds the agent logic. Tools are the bridge. The whole workshop is about making that bridge select and use evidence correctly.
